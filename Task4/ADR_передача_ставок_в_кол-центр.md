### **Название задачи:** Передача актуальных ставок в кол-центр банка и партнёрский кол-центр

### **Автор:** Дмитрий

### **Дата:** 11.11.2026

### **Функциональные требования**

| № | Действующие лица или системы | Use Case | Описание |
|---|---|---|---|
| UC1 | Сотрудники бэк-офиса, АБС | Публикация ставки | 1. Сотрудник депозитов изменяет публичные условия. 2. При необходимости выполняется согласование. 3. АБС сохраняет новую версию с датой начала действия и временем изменения. Только опубликованная версия доступна кол-центрам. |
| UC2 | АБС, контур публикации, система кол-центра | Обновление ставок банка | 1. Синхронизатор получает новую версию из АБС. 2. Передаёт полный набор публичных ставок в Rates API кол-центра. 3. Кол-центр атомарно обновляет read model и сохраняет номер версии. |
| UC3 | Оператор, система кол-центра | Консультация клиента | 1. Оператор открывает экран ставки во время звонка. 2. Видит действующие публичные условия и время последнего обновления. 3. Консультирует клиента, не делая прямой запрос в АБС. |
| UC4 | Контур публикации, SFTP, партнёр | Выгрузка партнёру | 1. После публикации новой версии генератор создаёт полный файл. 2. В файл включаются продукт, срок, диапазон суммы, ставка, версия и время формирования. 3. Файл и контрольная сумма передаются по SFTP. 4. Партнёр загружает последний файл во внешнюю систему. |
| UC5 | Оператор партнёра, внешняя система | Консультация партнёром | 1. Оператор использует последний полученный файл и скрипт банка. 2. Называет публичные условия. 3. Не обещает персональную или специальную ставку — такие условия рассчитывает банк. |
| UC6 | Контур публикации, эксплуатация | Ошибка доставки | 1. Компонент фиксирует ошибку обновления или SFTP. 2. Выполняет повтор без создания новой бизнес-версии. 3. Если последняя доставленная версия отстаёт от АБС, эксплуатация получает оповещение. |

### **Нефункциональные требования**

| № | Требование |
|---|---|
| NFR1 | АБС остаётся единственным источником ставок. В кол-центрах хранится только read model, а не независимо редактируемая копия. |
| NFR2 | Новые компоненты работают 24/7 с доступностью 99,9%. Чтение ставок оператором не зависит от текущей доступности АБС. |
| NFR3 | Обновление внутреннего кол-центра выполняется при публикации новой версии; расписание используется для контрольной синхронизации. Конкретный допустимый интервал отставания должен согласовать бизнес с эксплуатацией. |
| NFR4 | Оператор видит версию/время последнего обновления. Для партнёра те же признаки содержатся в файле и его имени. |
| NFR5 | Обновление read model атомарно. Повтор одной версии не меняет результат и не создаёт дубликаты. |
| NFR6 | Внутренние API защищены TLS и служебной аутентификацией. Для партнёра используется SFTP с отдельной учётной записью и доступом только к выделенному каталогу. |
| NFR7 | В файле и API кол-центра нет персональных данных, персональных/специальных ставок и внутренних параметров кредитного риска. |
| NFR8 | Запросы к АБС выполняет только интеграционный компонент с ограничением частоты. Экраны 200 операторов и 100 операторов партнёра не создают нагрузку на Oracle. |
| NFR9 | Ошибки и отставание версий наблюдаемы. Эксплуатация может вручную повторить доставку уже сформированной версии. |
| NFR10 | Для внутреннего кол-центра используются Java Spring Boot и PostgreSQL; файловая публикация размещается в контуре заявок на имеющемся MS SQL. |

### **Решение**

[Диаграмма контекста C4](c4-context.svg)

[Диаграмма компонентов C4](c4-components.svg)

Модуль ставок АБС, появившийся в MVP открытия депозитов, становится источником и для консультаций. Дополнительный контур публикации получает только опубликованные публичные версии. Черновики и специальные условия, которые ещё согласуются, операторам не попадают.

Для внутреннего кол-центра в существующей платформе подрядчика добавляются Rates API и небольшая read model в PostgreSQL. Это согласуется с текущим Spring Boot-стеком; в команде АБС есть Java-специалисты, которые могут участвовать в изменениях. Синхронизатор отправляет полную версию, а не набор неупорядоченных изменений. Rates API заменяет текущий снимок в одной транзакции, поэтому во время звонка оператор не увидит часть старых и часть новых условий.

Чтение выполняется из PostgreSQL кол-центра. При временной недоступности АБС последний снимок остаётся доступным, а экран показывает его время. Это важнее, чем синхронная «свежесть любой ценой»: прямые запросы 200 операторов к перегруженной АБС создали бы новый пик нагрузки после маркетинговой кампании.

**Файл для партнёра**

Партнёр не может вызывать API, поэтому для него используется тот же опубликованный снимок, но в файловом виде. Формат — CSV или XLSX, который партнёр подтверждает на этапе интеграционного тестирования. Каждая выгрузка полная: партнёру не нужно применять цепочку инкрементов.

Файл содержит `rate_version`, `generated_at`, продукт, срок, диапазон суммы и ставку. Рядом передаётся контрольная сумма. SFTP-компонент сначала пишет во временное имя и только после завершения переименовывает файл, чтобы внешняя система не забрала неполный документ. Учётная запись партнёра имеет доступ только к своему каталогу.

Версия и время должны быть видны внутри файла, а не только в имени. Если выгрузка задержалась, у банка есть основание для оповещения: версия последней успешной доставки не совпадает с последней опубликованной в АБС. Состояние публикаций и результатов доставки хранится в MS SQL контура заявок.

Периодическая контрольная синхронизация нужна даже при обновлении по событию. Она позволяет обнаружить пропущенное сообщение или ошибочно удалённый файл. Повторная отправка использует прежний номер версии и не меняет бизнес-условия.

### **Альтернативы**

| Вариант | Оценка |
|---|---|
| Операторы внутреннего кол-центра запрашивают АБС напрямую | Не принят. Рост звонков после кампании попадёт в Oracle, а отказ АБС оставит операторов без условий. |
| Бизнес отправляет Excel обоим кол-центрам по почте | Сохраняет ручной труд и не даёт контроля версии. Велика вероятность, что два оператора будут консультировать по разным файлам. |
| Для партнёра разработать API | Технически возможно в будущем, но сейчас внешняя система его не поддерживает. SFTP — единственный подтверждённый канал. |
| Реплицировать таблицы Oracle напрямую в PostgreSQL | Связывает системы физической схемой АБС и усложняет фильтрацию данных. Нужен именно публичный прикладной снимок, а не копия учётных таблиц. |

### **Недостатки, ограничения, риски**

- Партнёр получает условия с задержкой файлового обмена. Если его система не загрузит новый файл, банк увидит только факт доставки на SFTP, но не факт применения файла; это нужно проверять в пилоте и закрепить в регламенте.
- Показ времени обновления не устраняет риск консультации по устаревшим данным. При расхождении оператор должен ориентироваться на регламент и эскалировать вопрос, а не рассчитывать ставку самостоятельно.
- Полный файл проще инкрементов, но требует контроля размера и формата. Изменение структуры без версионирования может сломать загрузку у партнёра.
- Дополнительная read model требует наблюдения за отставанием. Без метрики «последняя версия АБС / последняя версия канала» скрытая ошибка синхронизации может сохраняться долго.
- SFTP усиливает требования к хранению ключей, сетевому доступу и ротации учётных данных. Доступ к каталогу нельзя выдавать другим подрядчикам.
- Если модуль ставок АБС не будет готов, файловая выгрузка всё равно потребует временного источника. Возврат к ручной рассылке Excel в качестве постоянного решения не предполагается.
